# mtncloud_managed_kubernetes_cluster

A managed Kubernetes cluster, built from MTN's Kubernetes layouts as MTN's own cluster order builds it: the masters from `master`, the workers from `worker` where it is set and the master's settings otherwise, every node with a fixed 100 GB root disk and no public IP, and the `MK8S` label. The security groups must allow the Kubernetes API (TCP 6443) and the kubelet (TCP 10250) between the nodes. Only a Customer Admin or Power User login can run kubectl on it from the console. MTN Cloud's console can show a cluster that built fine as `error` with "No kube masters found": when every master and worker is provisioned and the build reports complete, the cluster counts as built and can be changed in place, and `status` still shows `error`.

## Example Usage

```terraform
# A Kubernetes cluster with three masters and three workers that can scale to six, and bigger
# workers than masters. Every node gets a fixed 100 GB root disk plus the data disks below.
resource "mtncloud_managed_kubernetes_cluster" "apps" {
  name        = "apps"
  layout      = "ha3"
  project     = "web-prod"
  description = "Storefront workloads"
  labels      = ["storefront"]

  kubernetes_version = "1.35.3"
  pod_cidr           = "10.244.0.0/16"
  service_cidr       = "10.96.0.0/12"

  master = {
    plan            = "G2S4"
    data_volume     = [{ size = 50 }]
    networks        = ["app-net"]
    security_groups = ["k8s-nodes"] # allows TCP 6443 and 10250 between the nodes
  }

  worker_count = 3
  worker = {
    plan        = "G4S16"
    data_volume = [{ size = 200, datastore = "ENCR_AT_REST" }]
  }

  autoscaling = {
    min_nodes = 3
    max_nodes = 6
  }
}
```

## Import

Import is supported using the following syntax:

```shell
# Imported by its numeric ID (Infrastructure > Clusters).
terraform import mtncloud_managed_kubernetes_cluster.apps 42
```

MTN Cloud doesn't report what the nodes were built with (plans, disks, networks, versions), so after
an import those come from your configuration. The first apply after an import (which needs the cluster `ok`) records them, and only changes
what can change in place (name, description, labels, worker count); the `autoscaling` in your configuration is
adopted as it is. A Docker cluster can't be
imported here: use `mtncloud_docker_cluster`.

## Notes

- **Built like MTN's own order.** The cluster is built the way MTN's Managed Kubernetes catalog order builds it:
  a fixed 100 GB root disk on every node, your disks (at least one) as data disks, the `MK8S` label (added for you,
  not shown in `labels`), the description `MK8S Cluster` when you set none, your user created on every node, and
  the same networks and security groups on masters and workers unless `worker` says otherwise. The nodes get no
  public IP.
- **Disks.** The root disk is always 100 GB. `disk_datastore` names a datastore of the project for a node's disks
  (for example `ENCR_AT_REST`; `mtncloud_datastores` lists them), and a data disk's own `datastore` overrides it;
  left out, the project's default, `__DEFAULT__`. Workers use the master's unless `worker` sets their own.
- **Layouts.** `single` is `MTN Kubernetes Single-Master` (1 master), `ha3` is `MTN Kubernetes HA (3)` and `ha5`
  is `MTN Kubernetes HA (5)`. The layout sets the number of masters; `worker_count` sets the workers (3 if left out).
- **Security groups.** List groups that allow the Kubernetes API (TCP 6443) and the kubelet (TCP 10250) between the
  nodes. The project's default group is always applied. A group must be synced to the project.
- **Workers.** At least 3: MTN's layouts don't build a cluster with fewer.
- **Autoscaler.** Every cluster has its own autoscaler, installed by MTN's build with the range it was ordered with.
  That range is fixed when the cluster is built: MTN Cloud has no call that changes it later, so adding, changing
  or removing `autoscaling` afterwards is refused (rebuild with `terraform apply -replace` to change it). With
  `autoscaling`, the autoscaler moves the worker count between `min_nodes` and `max_nodes` and owns the count:
  `worker_count` is only the starting count, can't change after the build, and the current workers are in
  `worker_ids`. Without it, the autoscaler is built held at `worker_count` (MTN's order does the same: a cluster
  built with it off never finishes its workers), and `worker_count` changes in place by adding or removing workers.
  The autoscaler keeps the range it was built with, so it may remove an idle worker added above that count.
- **In place:** `name`, `description`, `labels`, `worker_count` without `autoscaling` (workers are added with the
  worker settings, and removed newest first) and the `worker` settings (used for workers added later). Everything
  else builds a new cluster.
- **Names are checked when you plan:** project, plans, networks, security groups, datastores, domain, registry,
  workflow and Kubernetes version. An unknown name lists the valid ones.
- **kubectl from the console** needs a Customer Admin or Power User login.
- **Built only when healthy.** An apply that creates or scales the cluster ends only when the cluster is `ok` and
  every worker is ready. If the cluster or a worker fails, the apply fails with MTN Cloud's message and names the failed
  workers. A create that fails, or isn't healthy when its wait ends, is kept in state and marked tainted: the next
  apply replaces it, and a destroy deletes it. With `worker_count` set in your configuration (with `autoscaling`, the autoscaler handles its workers), a worker that has failed isn't counted once the
  cluster settles: the next plan shows the cluster short, and its apply removes the failed worker and builds a new one.
- **"No kube masters found".** MTN Cloud's console can show a cluster that built fine as `error` with this message.
  When the build reports complete and every master and worker is provisioned, the cluster counts as built: the
  create succeeds, and the cluster can be changed in place. `status` still shows `error`, as MTN Cloud reports it.
  Any other error, or a failed node, still fails the apply.
- **Changes need a healthy cluster.** While `status` isn't `ok` (still building, failed, or warning), the plan
  warns about an in-place change and its apply fails, changing nothing. A destroy works in any state, whatever
  the configuration says, and
  `terraform apply -replace` (with no other change) rebuilds the cluster. A cluster that settles in `warning` is
  never healthy: its create fails when the wait ends, whatever the timeout.
- **Timeouts.** Create waits up to 90 minutes, updates and destroy up to 45 (see `timeouts`). If MTN Cloud is only
  slow, raise `timeouts.create` rather than letting the cluster be replaced.
- **Destroy** force-deletes the cluster with its infrastructure and associated instances (volumes too), in any
  state, including one still building.
