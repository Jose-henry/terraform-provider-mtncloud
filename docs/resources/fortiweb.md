# mtncloud_fortiweb

A FortiWeb web application firewall. Bring your own license. Ordered from MTN Cloud's catalog (Fortinet FortiWeb (BYOL)). An order is placed once: a changed input is refused at plan time, and nothing is deleted to order it again. Change the plan, labels, security groups, floating IP or data disks of the VMs it made with `mtncloud_instance_settings`. `terraform apply -replace=<address>` orders it again; add `lifecycle { prevent_destroy = true }` to stop that. The apply succeeds only when the order's workflow succeeded and every VM it made is running. The one exception: when the workflow succeeded and only the lookup of what it made failed, the apply succeeds with a warning and nothing is ordered again. `instance_ids` is then empty until the next refresh, so anything that indexes it in the same apply fails until you apply again. Inputs are checked at plan time against the item's live order form: what the form requires, its choices and its stated minimums. `terraform destroy` deletes what it made, shown under Instances in the console, with its disks and floating IPs, then the order's record in Catalog > Inventory. Secrets are write-only (Terraform 1.11 or newer): they are sent with the order and never stored. The order form doesn't let you name the VM: MTN names it from its template (`<initials>-<account>-MTN-CLOUD-<type>-<n>`), as in the console, and the provider finds it from the workflow's own report. `instance_names` shows the name it got. Each argument says what the Fortinet FortiWeb (BYOL) order form requires and allows (read 2026-11-06); every plan checks the live form. The form fills `name` itself, and they are sent as it fills them.

## Example Usage

```terraform
resource "mtncloud_fortiweb" "this" {
  project          = "web-prod"
  plan             = "G2S4"
  root_volume_size = 40
  networks         = ["app-net"]
  security_groups  = ["web"]
  floating_ip_pool = "public-network-01"
}
```

### Required

- `networks` (List of String) MTN Networks in the project, by name or ID. The first is the primary interface. For a network made in the same apply, give its ID (`mtncloud_network.x.id`): its name is known at plan, before the network exists. Order form: required. It says: "Note: Service requires at least 1 interface & at most 2 interfaces."
- `plan` (String) Plan (size), from the order form's own list: its name, or the size code in it (`G2S4` picks `Small (G2S4)`). An unknown plan lists the form's choices. Order form: required. It says: "Minimum recommended: 2 VPU & 8 GB."
- `root_volume_size` (Number) Root disk size in GB. At least 70 GB (the order form's minimum). It says: "Minimum recommended: 70 GB."

## Import

Import is supported using the following syntax:

```shell
# Imported by the ID of its catalog order (Catalog > Inventory).
terraform import mtncloud_fortiweb.this 9801
```

The order doesn't show what it was placed with, so the inputs come from your configuration: write them
exactly as ordered. The first apply after an import records them, finds the instances by name, and orders nothing.

## Notes

- **An order, not a live object.** Create places the catalog order, waits for MTN's workflow to
  finish, finds the instances it made by `name` in the project (`instance_ids`), and waits until
  they are running (`instance_statuses`). An instance that fails fails the apply with MTN Cloud's
  message; the resource is then tainted, so the next apply deletes it and orders again.
- **Placed once: a changed input is refused.** An order can't be edited, and Terraform won't
  delete what an order made to order it again, so a changed input stops the plan with
  `<input> can't change` and the value to set back. The plan, labels, security groups, floating IP
  and data disks of the instances it made change in place through `mtncloud_instance_settings`
  (the error says how). To order again on purpose, run `terraform apply -replace`; an instance
  that fails later also plans a replace. To stop a plan from deleting a server by accident, add
  `lifecycle { prevent_destroy = true }`.
- **Checked against the live order form.** MTN can change its order forms, so each plan checks
  the order against the form as it is now: the fields it requires (some only while another field
  is set), the fields it hides and fills itself, the values it pre-fills, and the limits its help
  text states (disk sizes, network counts, plan sizes). Plans are the form's own list. A field
  the form requires that has no argument here goes in `extra_inputs`.
- **Destroy deletes what the order made.** Its instances are deleted with their disks and floating
  IPs, then the order's record in Catalog > Inventory. A managed service is an app (under Apps in the
  console), so its app is deleted with all its instances. Another app is deleted only if it holds
  nothing but this order's instances; otherwise only the order's instances leave it. Destroy waits
  until they are gone (`timeouts { delete }`, default 90 minutes). It refuses, deleting nothing, while
  the order's workflow still runs past the timeout, after an import that hasn't been applied, or when
  nothing the order made can be found. To keep what it made, use a `removed` block
  (`lifecycle { destroy = false }`) or `terraform state rm` instead. If everything it made is
  deleted outside Terraform, the next plan orders it again.
- **Secrets are write-only** (Terraform 1.11 or newer): they are sent with the order and never stored
  in state or plans.
- **Names are checked when you plan**: project, plan, networks, security groups, floating IP pool,
  environment and every choice list (versions and so on) are looked up in MTN Cloud before anything
  is ordered, and an unknown value lists the valid ones. A floating IP pool must also be the external
  network of the router that holds the first network: another pool is an error, and no router a warning.
- **A failed workflow** is reported with MTN Cloud's message and nothing is kept; delete whatever it
  left in the console before applying again.
