# mtncloud_mongodb

A MongoDB server on its own VM. Ordered from MTN Cloud's catalog (MTN MongoDB). An order can't be changed once placed: changing any input replaces it (what the old order made is deleted, then a new one is ordered), and `terraform apply -replace=<address>` orders it again. Add `lifecycle { prevent_destroy = true }` to stop that. The apply succeeds only when the order's workflow succeeded and every VM it made is running. Inputs are checked at plan time against the item's live order form: what the form requires, its choices and its stated minimums. `terraform destroy` deletes what it made, shown under Instances in the console, with its disks and floating IPs, then the order's record in Catalog > Inventory. Secrets are write-only (Terraform 1.11 or newer): they are sent with the order and never stored. Each argument says what the MTN MongoDB order form requires and allows (read 2026-10-31); every plan checks the live form.

## Example Usage

```terraform
variable "admin_password" {
  type      = string
  sensitive = true
}

resource "mtncloud_mongodb" "this" {
  name             = "mongo-1"
  project          = "web-prod"
  plan             = "G2S4"
  root_volume_size = 40
  networks         = ["app-net"]
  security_groups  = ["web"]
  version          = "8.2"
  admin_username   = "admin"
  admin_password   = var.admin_password
}
```

## Import

Import is supported using the following syntax:

```shell
# Imported by the ID of its catalog order (Catalog > Inventory).
terraform import mtncloud_mongodb.this 9801
```

The order doesn't show what it was placed with, so the inputs come from your configuration: write them
exactly as ordered. The first apply after an import records them, finds the instances by name, and orders nothing.

## Notes

- **An order, not a live object.** Create places the catalog order, waits for MTN's workflow to
  finish, finds the instances it made by `name` in the project (`instance_ids`), and waits until
  they are running (`instance_statuses`). An instance that fails fails the apply with MTN Cloud's
  message; the resource is then tainted, so the next apply deletes it and orders again.
- **A changed input orders again.** An order can't be edited, so changing any input plans a
  replace: what the order made is deleted, then the item is ordered again. `terraform apply
  -replace` does the same on purpose, and an instance that fails later also plans a replace. To
  stop a plan from deleting a server by accident, add `lifecycle { prevent_destroy = true }`.
- **Checked against the live order form.** MTN can change its order forms, so each plan checks
  the order against the form as it is now: the fields it requires (some only while another field
  is set), the fields it hides and fills itself, the values it pre-fills, and the limits its help
  text states (disk sizes, network counts, plan sizes). Plans are the form's own list. A field
  the form requires that has no argument here goes in `extra_inputs`.
- **Destroy deletes what the order made.** Its instances are deleted with their disks and floating
  IPs, then the order's record in Catalog > Inventory. A managed service is an app (under Apps in the
  console), so its app is deleted with all its instances. Another app is deleted only if it holds
  nothing but this order's instances; otherwise only the order's instances leave it. Destroy waits
  until they are gone (`timeouts { delete }`, default 90 minutes). It refuses, deleting nothing, while
  the order's workflow still runs past the timeout, after an import that hasn't been applied, or when
  nothing the order made can be found. To keep what it made, use a `removed` block
  (`lifecycle { destroy = false }`) or `terraform state rm` instead. If everything it made is
  deleted outside Terraform, the next plan orders it again.
- **Secrets are write-only** (Terraform 1.11 or newer): they are sent with the order and never stored
  in state or plans.
- **Names are checked when you plan**: project, plan, networks, security groups, floating IP pool,
  environment and every choice list (versions and so on) are looked up in MTN Cloud before anything
  is ordered, and an unknown value lists the valid ones. A floating IP pool must also be the external
  network of the router that holds the first network: another pool is an error, and no router a warning.
- **A failed workflow** is reported with MTN Cloud's message and nothing is kept; delete whatever it
  left in the console before applying again.
