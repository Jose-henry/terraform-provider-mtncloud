# mtncloud_cluster

A Kubernetes or Docker cluster, built from MTN's cluster layouts. The masters (Docker: the hosts) are built from `master`; workers use `worker` where it is set and the master's settings otherwise.

## Example Usage

```terraform
# A Kubernetes cluster with three masters, three workers that can scale to six,
# bigger workers than masters, and a public IP on every node.
resource "mtncloud_cluster" "apps" {
  name        = "apps"
  layout      = "MTN Kubernetes HA (3)"
  project     = "web-prod"
  description = "Storefront workloads"
  labels      = ["storefront"]

  kubernetes_version = "1.35.3"
  pod_cidr           = "10.244.0.0/16"
  service_cidr       = "10.96.0.0/12"
  domain             = "localdomain"

  master = {
    plan             = "G2S4"
    root_volume_size = 50
    data_volume      = [{ size = 50 }]
    networks         = ["app-net"]
    security_groups  = ["default", "k8s-api"]
    floating_ip_pool = "public-network-01"
  }

  worker_count = 3
  worker = {
    plan        = "G4S16"
    data_volume = [{ size = 200, datastore = "ENCR_AT_REST" }]
  }

  autoscaling = {
    min_nodes = 3
    max_nodes = 6
  }
}

# A single Docker host.
resource "mtncloud_cluster" "builds" {
  name    = "builds"
  type    = "docker"
  project = "web-prod"

  master = {
    plan             = "G2S4"
    root_volume_size = 40
    data_volume      = [{ size = 100 }]
    networks         = ["app-net"]
  }
}
```

## Import

Import is supported using the following syntax:

```shell
# Imported by its numeric ID (Infrastructure > Clusters).
terraform import mtncloud_cluster.apps 42
```

MTN Cloud doesn't report what the nodes were built with (plans, disks, networks, versions), so after an
import those come from your configuration. The first apply after an import records them, and only
changes what can change in place (name, description, labels, worker count, autoscaling).

## Notes

- **Layouts.** Only MTN's layouts can be built: `MTN Kubernetes Single-Master` (1 master), `MTN Kubernetes HA (3)`,
  `MTN Kubernetes HA (5)` and `MTN Docker Cluster`. `mtncloud_cluster_layouts` lists them.
- **Masters and workers.** `master` is required: a plan, a root disk, at least one data disk and at least one
  network. Workers use the `worker` block where it is set and the master's settings otherwise.
- **In place:** `name`, `description`, `labels`, `worker_count` (workers are added with the worker settings, and
  removed newest first), the `worker` settings (used for workers added later) and `autoscaling`. Everything else
  builds a new cluster.
- **Autoscaling.** With `autoscaling`, the autoscaler moves the worker count between `min_nodes` and `max_nodes`;
  `worker_count` is then only the starting count, and the current workers are in `worker_ids`.
- **Names are checked when you plan:** layout, project, plans, networks, security groups, datastores, floating IP
  pool, domain, registry, workflow and Kubernetes version. An unknown name lists the valid ones.
- **Timeouts.** Create waits up to 90 minutes, updates and destroy up to 45 (see `timeouts`). If the cluster isn't
  ready when the wait ends, it is kept with a warning and never built twice.
- **Destroy** deletes the cluster with its nodes.
