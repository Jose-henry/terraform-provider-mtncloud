# Changelog

All notable changes to this provider. Format: [Keep a Changelog](https://keepachangelog.com), versions: SemVer.

## 0.6.0 (2026-10-29)

- New: `mtncloud_load_balancer_l7_policy`, a layer 7 policy on an `HTTP` or `TERMINATED_HTTPS` listener with its rules: requests that match are sent to another pool (`REDIRECT_TO_POOL`), redirected (`REDIRECT_TO_URL`, `REDIRECT_PREFIX`) or rejected. Everything changes in place except the listener; the rules are replaced together. A refused rule leaves no policy behind. What each action needs is checked at plan time. Number a listener's policies 1, 2, 3 without gaps: the cloud refuses a position another policy holds, so a new policy can only go after the last one (the error says so). Policies created in one apply are made in position order, whatever order Terraform starts them in. After a policy is deleted the cloud closes the gap; the ones below it report a lower position, which is no change. `invert` defaults to `false`; `redirect_http_code` keeps its last value when taken out. Import: `<network_id>/<load_balancer_id>/<listener_id>/<l7_policy_id>`. Data sources `mtncloud_load_balancer_l7_policies` (a listener's policies, in the order they are tried) and `mtncloud_load_balancer_l7_policy`.
- New: `mtncloud_load_balancer_instance_member`, an instance in a pool: every address it has on the load balancer's network becomes a member, and the console keeps the pool in step as the instance scales. Changing the port, weight or `backup` replaces the members. One per instance and pool: create refuses an instance that already has members in the pool (import them instead). Import: `<network_id>/<load_balancer_id>/<pool_id>/<instance_id>`.
- New: `mtncloud_load_balancer_floating_ip`, a public IP on a load balancer, from a pool by name (checked at plan time, with the available pools on a miss) or an address the project holds. `release_on_destroy` (default `true`) gives the address back on destroy. An address detached in the console is attached again at the next apply. Create refuses a load balancer that already has a public IP (import it instead). Setting or changing `floating_ip_pool` replaces the address with a new one from the pool; after an import, keep `floating_ip_id` in the configuration. Import: `<network_id>/<load_balancer_id>/<floating_ip_id>`; an imported address is kept on destroy (`release_on_destroy = false`) until the configuration is applied, so the first plan after an import shows that change.
- New data source: `mtncloud_load_balancer_member`, one member of a pool by ID or name.
- Changed: `mtncloud_cluster` (masters and workers) and catalog orders with security groups now always apply the project's default security group, as `mtncloud_instance` does, with the groups you list added to it. Listing the default too changes nothing. Only what is sent on create changes: existing clusters and orders show no diff.
- Fixed: a load balancer piece create that lost its answer finds an L7 policy by its request tag too, so it is never made twice.
- New: `mtncloud_archive_file`, a file in an archive (up to 512 MiB) from `content`, `content_base64` or a local `source`, uploaded again when the content changes; the file keeps its ID. Name the archive by name (`archive`) or ID (`archive_id`). A file changed in the console (another size) is uploaded again; one deleted there is made again. Create refuses a path that already holds a file, since the upload would overwrite it. Import by ID or `<archive>/<path>`.
- New: `mtncloud_archive_file_link`, a download link anyone can use without logging in, for `expire_seconds` (`0`: never expires). Its URL and secret are sensitive and kept in state. An expired link is made again at the next apply. Import: `<file_id>/<link_id>`.
- New data source: `mtncloud_archive_files`, the files and folders in one folder of an archive, or every file under it.
- New: `mtncloud_archive_bucket`, an archive (Tools > Archives) whose files are kept in a MOS bucket (D-034). Name the bucket by its MOS name (`mos_bucket`) or its console record ID (`mos_bucket_id`, for example `mtncloud_mos_bucket.x.id`); the plan checks it. Name, description and `public_url` change in place; another bucket replaces the archive. Destroy deletes the archive and its files, also from the MOS bucket, so it refuses while the archive holds files unless `force_destroy` is set. Import by ID or name. Data sources `mtncloud_archive_bucket` (by ID or name) and `mtncloud_archive_buckets`.
- Docs: a username login can name the tenant by its numeric account ID instead of its subdomain (`tenant_subdomain = "42"`, or `MTNCLOUD_API_TENANT`). Both work.
- New load balancer resources (D-033): `mtncloud_load_balancer`, `mtncloud_load_balancer_listener`, `_pool`, `_member` and `_health_monitor`, each changed on its own, so a change to one never touches the others. The VIP defaults to the network's own subnet. The load balancer's name, description, tags and `enabled` change in place; its network, VIP subnet and VIP address replace it. `enabled = false` takes the whole load balancer out of service. A listener's protocol and port, a pool's protocol, a member's address and port and a monitor's type replace that piece. Taking out a listener's description or SNI certificates, or a member's health-check address or port, clears it in place; a `TERMINATED_HTTPS` listener must keep its `tls_certificate_ref` (a plan-time error otherwise). A listener has a `description`. A create that timed out or lost its answer is retried safely: the cloud recognises the retry and returns the piece it already made, so nothing is made twice. Changes to one load balancer run one at a time, and each waits until the load balancer is `ACTIVE` again (a create takes about 2 minutes). Members are servers by address for now. Import: `<network_id>/<load_balancer_id>`, then the piece's path (see each resource's page).
- New: MOS (MTN Object Storage) resources (D-032). `mtncloud_mos_bucket` creates a bucket and lists it in the console under Infrastructure > Storage > Buckets; import by console ID or bucket name. Destroy refuses while an archive uses the bucket (the console would delete the archive with it) and while the bucket holds objects, unless `force_destroy` is set. Its settings are separate resources: `mtncloud_mos_bucket_acl`, `_bucket_cors`, `_bucket_lifecycle` (expiry by prefix, after days or on a date, and cleanup of unfinished uploads), `_bucket_logging` and `_bucket_object_lock` (default GOVERNANCE retention). `mtncloud_mos_object` uploads a file from `content`, `content_base64` or a local `source` (uploaded again when the file changes), with metadata, checksums and GOVERNANCE retention; `mtncloud_mos_object_acl` publishes one object.
- New MOS data sources: `mtncloud_mos_credentials` (the tenant's keys, sensitive), `mtncloud_mos_buckets`, `mtncloud_mos_bucket` (one bucket with all its settings), one per bucket setting, `mtncloud_mos_objects` (with prefix and folder listing), `mtncloud_mos_object` (with its content on request, up to 1 MiB) and `mtncloud_mos_object_acl`.
- The provider reads the tenant's MOS keys from Cypher, where the MOS catalog order puts them. `MTNCLOUD_MOS_ACCESS_KEY`, `MTNCLOUD_MOS_SECRET_KEY` and `MTNCLOUD_MOS_ENDPOINT` (`public`, `private` or a URL) override them.
- **Renamed:** `mtncloud_managed_kubernetes` is now `mtncloud_self_managed_kubernetes`. The cluster is built by MTN Cloud and run by you, so "managed" was wrong (D-030). The old name still works, with a deprecation warning, and will be removed in a later release. To switch with nothing replaced, rename the resource and add a `moved {}` block from the old address to the new one (Terraform 1.8 or newer). Destroy still goes through the cluster's app.
- Docs: `mtncloud_siem` is listed with the security appliances, not under managed services.
- New load balancer data sources: `mtncloud_load_balancers` (by network, with name and status filters), `mtncloud_load_balancer` (with its listeners, and its pools with members and health monitors), `mtncloud_load_balancer_listeners` and `_listener`, `_pools` and `_pool`, `_members`, `_health_monitors` and `_health_monitor`, and `mtncloud_load_balancer_floating_ip_pools`. Pick the load balancer by ID or name on its network. Each load balancer is read once per run, however many data sources ask about it; a read takes a few seconds.
- **Breaking:** `mtncloud_load_balancer` and `mtncloud_load_balancers` are replaced by the data sources above. The old ones read a list that is always empty on MTN Cloud, so they never returned a load balancer. What changes for a configuration that used them: both now need `network_id`; the singular's `id` is the load balancer's ID (a UUID string, not a number); the plural's `name_regex` is gone (use `name`, matched exactly, or `status`); and the old attributes `type`, `cloud`, `visibility`, `host`, `port`, `ip`, `internal_ip`, `external_ip` and `ssl_enabled` are gone (`vip_address` is the private address, `floating_ip` on the list the public one, and ports are on the listeners).
- Load balancer reads run a console job each. They add nothing to Automation > Jobs, but each shows in the job execution history as `tf-lb-<action>-<random>`.

## 0.5.0 (2026-10-28)

- `mtncloud_instance`: power control. `power_state` (`running`, `stopped`, `suspended`) powers the VM in place and puts back a change made in the console; left out, it only shows the state. A new `restart_trigger` value reboots the VM. A power call refused at create is a warning, so the new VM isn't tainted.
- **Changed:** destroying a catalog-order resource now deletes what the order made, instead of refusing (D-029). Its instances are deleted with their disks and floating IPs, through their app for the managed services (database, MQ, streaming and Kubernetes), then the order's record in Catalog > Inventory. An app that also holds other instances is kept. Destroy refuses, deleting nothing, when it can't tell what the order made. `mtncloud_letsencrypt_certificate` deletes nothing and warns; `mtncloud_project` still refuses. To keep what an order made, use a `removed` block before you destroy.
- Fixed: catalog services that build VMs were refused with "PLAN value [...] is not contained within the available options". The plan is now looked up in the order form's own plan list, by name, as the console does.
- Fixed: `mtncloud_credential` showed a change on every plan (the API's password hash was written into state), and an imported credential was replaced (its `type` wasn't read).
- `mtncloud_instance` and the catalog services check `floating_ip_pool` when you plan: a pool that isn't the external network of the router holding the (primary) network is an error naming the right one; no router is a warning.
- `mtncloud_instance`: a power change MTN Cloud accepts but doesn't start within 2 minutes (suspend, on some VMs) fails with a clear message instead of waiting out the timeout.
- `mtncloud_instances` filters by `network` (ID or name; a VM matches on any of its cards) and returns each instance's `networks`.
- Docs: the examples pin `~> 0.4`. An instance with `install_agent` on (the default) stays "provisioning" until its agent reports in, so its network must be on an MTN Router with an external network.

## 0.4.0 (2026-10-28)

- New resource `mtncloud_cluster`: Kubernetes (default) and Docker clusters from MTN's layouts, with master and worker settings, worker count and autoscaling changed in place, and every name checked when you plan.
- New data sources `mtncloud_registries` and `mtncloud_cluster_layouts`.

- New resource `mtncloud_ssl_certificate`: upload a certificate, chain and private key. The key is write-only and is sent again when `private_key_version` changes.

- New resources for MTN's catalog, one per item (D-026): `mtncloud_mysql`, `mtncloud_postgresql`, `mtncloud_mariadb`, `mtncloud_mongodb`, `mtncloud_lamp_stack`, `mtncloud_lemp_stack`, `mtncloud_wordpress`, `mtncloud_apache_web_server`, `mtncloud_nginx_web_server`, `mtncloud_managed_database`, `mtncloud_managed_mq`, `mtncloud_managed_streaming`, `mtncloud_managed_kubernetes`, `mtncloud_siem`, `mtncloud_vpn_service`, `mtncloud_wireguard_vpn`, `mtncloud_bastion_host`, `mtncloud_fortinet_firewall`, `mtncloud_fortiweb`, `mtncloud_fortiadc`, `mtncloud_fortimanager`, `mtncloud_fortianalyzer` and `mtncloud_letsencrypt_certificate`. Every name (project, plan, networks, security groups, floating IP pool, versions and other choices) is checked when you plan. Orders can't be changed or destroyed from Terraform, like projects (D-028); secrets are write-only (Terraform 1.11 or newer).
- New resources `mtncloud_nfs_share` and `mtncloud_smb_share`: created, updated (quota, clients, SMB password) and deleted through their catalog orders.

- **Removed** the integration resources (`mtncloud_ansible_integration`, `mtncloud_ansible_tower_integration`, `mtncloud_chef_integration`, `mtncloud_docker_registry_integration`, `mtncloud_git_integration`, `mtncloud_puppet_integration`, `mtncloud_servicenow_integration`, `mtncloud_vro_integration`): integrations are set up in the console. Run `terraform state rm` on any you manage before upgrading. The integration data sources stay, for tasks that need an integration ID.

- Docs: the examples now pin `~> 0.3`.
- New data sources, singular (by `id` or name) and plural (with `name_regex`): `app(s)`, `ssl_certificate(s)`, `load_balancer(s)`, `cluster(s)`, `catalog_order(s)` (what you ordered, with status), `user(s)`, `identity_source(s)`, `form(s)`; plural only: `user_roles`, `network_subnets`, `storage_buckets`, `storage_volumes`, `domains`, `key_pairs`, `credentials`, `workflows`, `jobs`, `integrations`, `cyphers` (keys and leases, never values); singular only: `project` (with group and cloud), `router`, `security_group` (with every rule), `datastore`, and `cypher` (reads one existing key on any mount, value sensitive; never creates one).
- New resources `mtncloud_cypher_password`, `mtncloud_cypher_uuid` and `mtncloud_cypher_key`: values MTN Cloud generates and keeps in Cypher, with an optional lease (`ttl`). The value is in state, marked sensitive. An existing key is never overwritten, and a refresh never re-creates a deleted one.
- New task resources for the task types the console offers that had none: `mtncloud_ai_task`, `mtncloud_conditional_workflow_task`, `mtncloud_dynamic_wallet_collection_task`, `mtncloud_http_task`, `mtncloud_powerscale_storage_collection_task`, `mtncloud_puppet_agent_install_task` and `mtncloud_reverse_text_task`. AI agents, Puppet masters, workflows and credentials are given by name.
- Provider `project`, `group` and `cloud` (or `MTNCLOUD_PROJECT`, `MTNCLOUD_GROUP`, `MTNCLOUD_CLOUD`): resources that leave out `project` (instance, network, router, security group) or `group` (instance) use them, and `group`/`cloud` choose among several when your account has more than one. State keeps the value used, so changing the provider's `project` later replaces resources that rely on it.
- The same project written another way (`web-prod` or `web-prod-Acme`) on a network, router or security group is no longer a one-time in-place update: the plan is empty.
- List data sources take filters on what the API returns for each object: `status`, `type`, `group`, `cloud`, `visibility`, `environment`, `enabled`, `active` and similar (text matched with case ignored), and `labels` (every one given must be there). `mtncloud_instances` also filters by `image`, `plan` and `tags`, and returns tags; `mtncloud_networks` by `status` and `labels`.
- New data sources `mtncloud_image` (by name or code) and `mtncloud_floating_ips` (the public IPs on your instances; the floating IP endpoint refuses customer logins).
- `mtncloud_instance` and `mtncloud_instances` return `group` and `cloud`.
- **Breaking:** `mtncloud_networks` is rebuilt: `name_regex` and `project` replace `cloud_id`, `sort_ascending` and `filter`; it keeps `ids` and adds `networks`, each with project, group, cloud, CIDR, gateway and status.
- New data source `mtncloud_catalog_item`: one service from the catalog, with the inputs its order form asks for.
- Docs: datastore examples use `__DEFAULT__`, the default datastore.
- **Breaking:** removed what customers can't create in MTN Cloud's Library: instance types, layouts, node types, cluster layouts, file and script templates, boot and preseed scripts, security packages, blueprints, spec templates and catalog items, with their lookups; the Groovy, JavaScript, Python and jRuby script tasks; the cloud type and provision type lookups; and the `mtncloud_cypher_secret` data source (a `mtncloud_cypher` lookup replaces it).
- **Breaking:** removed the 36 resources and 12 data sources only the MTN Cloud master tenant can use (tenants, appliance settings, policies, service plans, prices, licenses, cloud and resource pool lookups and others). Customers pick sizes with `mtncloud_plans` and datastores with `mtncloud_datastores`.
- Fixed: instances made in the console showed an empty `private_ip`.
- Fixed: `mtncloud_plans` accepts the image by name (for example `MTN Ubuntu Server 24.04.3LTS`) as well as by code.
- `mtncloud_network` (data source) is rebuilt: look up by ID or name, optionally in a project; it now returns the network's `project`, `group`, `cloud`, gateway, DNS, DHCP and subnet ID.

## 0.3.0 (2026-10-27)

0.1.0 and 0.2.0 were tagged without their own sections, so this list covers everything since the fork.

- New data sources `mtncloud_routers`, `mtncloud_instances` and `mtncloud_instance`: look up MTN Routers and instances, including those made in the console, by name or ID.
- `mtncloud_instance`: an attach whose address hasn't shown when the timeout ends is never sent again (no second address); a warning shows until it appears. A timeout message now suggests raising `timeouts`.
- Removed the "Sharing Data Between Apps/Instances" guide: it needs master-only secret policies.
- Docs: removed a deprecation notice and an outdated TLS warning carried over from the upstream provider; neither applied to this provider. The front page now describes MTN Cloud, and the examples pin a version.
- Forked from the upstream provider (MIT) and renamed to `mtncloud` (`mtn/mtncloud`).
- Scope reduced to MTN Cloud: removed AWS, Azure, vSphere, standard and MVM clouds and instances, ARM and CloudFormation blueprints and spec templates, and the `cloud_folder` data source. `cloud_datastore` was restored (later removed as master-only).
- Environment variables renamed to `MTNCLOUD_API_*`.
- **Breaking:** TLS certificate verification is now on by default (`secure` defaults to `true`). For a console with a self-signed certificate, set `secure = false` or `MTNCLOUD_API_SECURE=false`.
- `url` is optional in the schema (it can come from `MTNCLOUD_API_URL`); a clear error is shown when neither is set.
- Sub-tenant login now sends `subdomain\username` with a single backslash.
- New data sources that pick things by name, using endpoints customer roles can call: `mtncloud_projects`, `mtncloud_images`, `mtncloud_plans`, `mtncloud_datastores`, `mtncloud_security_groups`, `mtncloud_external_networks`, `mtncloud_catalog_items`.
- The provider now serves the legacy and Plugin Framework implementations together (terraform-plugin-mux).
- The provider address is `jose-henry/mtncloud` on the public Terraform Registry (D-021).
- New resource `mtncloud_project`: orders MTN's "Create Project" catalog item and waits for its workflow, not for the project to sync in (allow up to an hour). Name and description can't change; destroy is refused (use a `removed` block). Import by the catalog order ID.
- `mtncloud_instance` accepts `floating_ip_pool`: a public IP attached once the VM runs, changed in place, shown in `public_ip`. The apply waits for the address and fails if it isn't attached.
- `mtncloud_instance` accepts `scale` (automatic scaling on CPU, memory or disk usage, changed in place) and `expire_days`/`shutdown_days` (set at create; `expire_date` and `shutdown_date` show the dates).
- New resource `mtncloud_instance`: a VM by names (group, project, image, plan, security groups, datastores, environment, domain), checked at plan time. The name is optional (the tenant's naming template applies), data volumes and networks are added in place, a plan change restarts the VM in place, and the project's default security group is always applied. Waits until running, with `timeouts`.
- `mtncloud_network` now waits until MTN Cloud reports a new network ready, and accepts `timeouts { create }`.
- New resource `mtncloud_router` (MTN Router): connects networks of a project, with an optional gateway; waits until ready, with `timeouts`.
- New resource `mtncloud_network` (MTN Network): project by name, DNS defaulting to MTN's resolvers, optional IPv6, and the subnet ID for routers.
- API refusals sent as a 2xx response with `"success": false` are now reported as errors with MTN Cloud's message.
- New resources `mtncloud_security_group` (rules as a set, every rule visible in `all_rules`, optional removal of the default allow-all egress rules) and `mtncloud_security_group_rule`. Both work with a customer (sub-tenant) login.
- 36 resources and 12 data sources that MTN Cloud only allows for the master tenant now say so in the first line of their description, and the features guide shows which types a customer (sub-tenant) login can use.
